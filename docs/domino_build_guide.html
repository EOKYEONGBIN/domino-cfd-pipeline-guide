01

환경 설치 - OS부터 PyTorch까지

왜 이 순서인가: 아래 각 레이어는 그 위 레이어가 요구하는 최소 조건입니다 - 커널이 GPU를 인식해야 드라이버가 의미 있고, 드라이버가 있어야 CUDA 런타임이 GPU를 쓸 수 있고, 그 위에서야 PyTorch/physicsnemo가 동작합니다. 실제로 A6000 워크스테이션에 설치했던 순서를(로그 확인) 그대로 따릅니다.

1-1. OS: Ubuntu (Linux)

Windows가 아니라 Linux를 쓰는 이유는 단순합니다 - physicsnemo/warp-lang이 공식적으로 지원, 검증하는 플랫폼이 Linux이기 때문입니다. 실제 설치 환경: Ubuntu 26.04 LTS, 커널 7.0.0-generic. Ubuntu의 HWE(Hardware Enablement) 커널 계열을 쓰면 최신 GPU 세대에 대한 커널 모듈 지원이 더 빠르게 들어옵니다.

1-2. NVIDIA 드라이버 설치

왜: 커널이 GPU 하드웨어와 대화하려면 드라이버가 필요합니다. 이게 없으면 nvidia-smi조차 실행이 안 됩니다 - CUDA도, PyTorch도 그 이전 단계라 의미가 없습니다.

Shell - 드라이버가 뭘 추천하는지 먼저 확인
sudo apt update && sudo apt upgrade -y
ubuntu-drivers devices        # 이 GPU에 맞는 드라이버 후보를 보여줌
sudo ubuntu-drivers install   # 추천 드라이버 자동 설치
sudo reboot                   # 새 커널 모듈을 실제로 로드하려면 재부팅 필수

ubuntu-drivers install은 내부적으로 GPU 세대에 맞는 정확한 패키지(이 경우 nvidia-driver-595-open, 오픈소스 커널 모듈 변형)를 골라 apt-get install을 실행해줍니다 - NVIDIA 사이트에서 .run 설치 파일을 받아 수동 설치하는 것보다 안전합니다(커널 업데이트 시 apt가 알아서 같이 관리해줌).

주의: 버전에 따라 명령어가 다릅니다

ubuntu-drivers-common 패키지가 새 버전(1:0.10.9+)으로 올라가면 하위 명령어가 autoinstall에서 install로 바뀝니다. Error: No such command 'autoinstall'가 뜨면 패키지가 업데이트된 것이니 위처럼 install을 쓰세요 (ubuntu-drivers --help로 현재 버전이 지원하는 하위 명령어 확인 가능).

재부팅 후 검증
nvidia-smi
# NVIDIA-SMI 595.91.07  Driver Version: 595.91.07  CUDA Version: 13.0
# 위 처럼 GPU 이름/메모리/드라이버 버전이 보이면 성공
경고: 워크스테이션이라면 전력/발열도 이 시점에 정리

사무실, 연구실에 상시로 두는 워크스테이션이면, 학습 도중 전력 소비, 발열, 소음이 문제가 될 수 있습니다. 드라이버 설치 직후 전력 상한을 낮춰서 실험해보고 고정하세요 (실제로 250에서 300, 150, 175, 160, 165W 순서로 시험해서 165W 부근으로 확정한 사례):

sudo nvidia-smi -pl 165   # 전력 상한(W) 설정
sudo nvidia-smi -rgc      # GPU 클럭을 기본값으로 리셋

1-3. CUDA - 별도로 설치하지 않습니다

확인: 흔한 오해

"CUDA 설치"라고 하면 보통 NVIDIA 사이트에서 CUDA Toolkit(nvcc 컴파일러 포함)을 따로 받아 까는 걸 떠올리기 쉽지만, 이 파이프라인에서는 시스템 전역 CUDA Toolkit을 설치하지 않았습니다. 실제로 /usr/local/cuda 자체가 없고 nvcc 명령도 없습니다. 대신:

  • PyTorch를 CUDA 런타임이 이미 내장된 wheel로 설치합니다 (torch==2.14.0+cu130의 +cu130이 바로 그 표시) - 별도 설치 없이 그 자체로 GPU를 씁니다.
  • physicsnemo의 GPU 커널(warp-lang)은 실행 중에 NVIDIA 드라이버가 제공하는 컴파일러(NVRTC)로 필요한 커널을 그때그때 즉석 컴파일합니다 - 이것도 시스템 CUDA Toolkit이 필요 없습니다.

즉 "드라이버 버전이 지원하는 최신 CUDA"와 "PyTorch wheel이 요구하는 CUDA 버전"만 맞으면 되고, 그 사이에 사람이 따로 설치할 레이어는 없습니다.

AhmedML이 어떤 시뮬레이션인가

Ahmed body는 1984년 S.R. Ahmed가 제안한, 자동차 공기역학 연구의 표준 벤치마크 형상입니다. 실제 차량의 복잡한 디테일(사이드미러, 바퀴 디테일 등) 없이도, 자동차 뒷면에서 일어나는 압력 유도 유동 박리(pressure-induced separation)와 3차원 와류 구조를 그대로 재현합니다 - "뒤쪽 경사면 각도에 따라 항력이 어떻게 바뀌는가"라는, 실제 차량 설계에서 가장 중요한 공기역학 현상 중 하나를 단순한 형상으로 연구할 수 있게 해줍니다.

AhmedML(caemldatasets.org/ahmedml, arXiv:2407.20801)은 이 고전적 형상을 500가지로 파라메트릭하게 변형해 OpenFOAM으로 시뮬레이션한 CFD-AI 학습용 데이터셋입니다. 실제로 받은 geo_parameters_10.csv를 열어보면 케이스마다 바뀌는 8개 형상 파라미터를 그대로 확인할 수 있습니다:

시뮬레이션 조건 (OpenFOAM v2212, 시간정확도 hybrid RANS-LES, 약 2천만 셀, 약 80 대류시간단위 동안 해석):

  • 비압축성 저속 유동, 무차원 컨벤션 - 자유류 속도 U_inf = 1 m/s, 밀도 rho = 1 (실제 도로 주행 속도가 아니라, 압력이 이미 운동압으로 스케일된 값이라는 뜻)
  • 차체 높이 H = 0.288 m 기준 레이놀즈수 Re 약 7.68x10^5 (동점성계수 nu = 3.75x10^-7 m^2/s)

배치 다운로드 (디스크 가드 포함, Shell)
MIN_FREE_GB=100
check_disk_space() {
    local avail=$(df --output=avail -BG / | tail -1 | tr -dc '0-9')
    if [ "$avail" -lt "$MIN_FREE_GB" ]; then
        echo "ABORT: ${avail}GB free < ${MIN_FREE_GB}GB floor" >&2; exit 1
    fi
}

# 60개씩: 다운로드 -> 전처리 -> 원본 삭제, 반복 (전체를 한 번에 받지 않음)
for batch in $(split_into_batches manifest.txt 60); do
    check_disk_space
    download_batch "$batch"          # wget으로 stl/vtp/(vtu)/csv
    python process_data.py --config-name my_config \
        ++data_processor.input_dir=raw/$batch \
        ++data_processor.output_dir=processed/train
    delete_raw_if_processed "$batch"  # .npy 존재 확인 후에만 삭제
done

04

학습 설정 - 안전장치를 먼저 넣는다

왜: 공식 예제의 train.py는 "best validation loss"를 로그에 출력만 하고 저장하지 않습니다. 이걸 나중에 알아차리면 이미 수백 GPU-시간을 날린 뒤입니다.

model.model_type은 surface부터 시작하세요 (volume 브랜치 없이 더 빠르게 검증 가능, 이후 combined로 확장).

train.py에 반드시 추가할 것 (Python)
# best-checkpoint 저장 + early stopping + 보존 정책
epochs_since_best = 0
early_stopping_patience = cfg.train.get("early_stopping_patience", None)

# --- 매 epoch, validation 직후 ---
if avg_vloss < best_vloss:
    best_vloss = avg_vloss
    epochs_since_best = 0
    save_checkpoint(best_model_path, models=model, optimizer=optimizer,
                     scheduler=scheduler, scaler=scaler, epoch=epoch)
    _keep_only_epoch(best_model_path, epoch)   # 이전 best 파일 삭제 (누적 방지)
else:
    epochs_since_best += 1

if (epoch + 1) % cfg.train.checkpoint_interval == 0:
    save_checkpoint(model_save_path, models=model, optimizer=optimizer,
                     scheduler=scheduler, scaler=scaler, epoch=epoch)
    _prune_periodic_checkpoints(model_save_path, keep_last=5)  # 최근 5개만 유지

if early_stopping_patience and epochs_since_best >= early_stopping_patience:
    break
경고: 이 세 가지가 없으면
  • Best 저장 없음 - 과적합 이후에도 계속 학습해서, 결국 가장 나쁜(마지막) 체크포인트가 배포됨
  • Early stopping 없음 - GPU 시간 낭비 (수백 epoch를 의미 없이 더 돌림)
  • 보존 정책 없음 - checkpoint_interval마다 파일이 쌓여서 디스크가 가득 참 (실제로 1000 epoch 학습에서 56GB까지 쌓인 사례 있음, 위 정책 적용 시 1.5GB)

06

본 학습 전 필수 게이트: Single-Case Overfit Test

왜: 전체 데이터로 큰 학습을 돌리고 나서야 "데이터가 나쁜지 파이프라인이 나쁜지" 구분하려 하면 너무 늦습니다. 케이스 1개로 5분 만에 미리 확인하세요.

케이스 1개만으로 train==val로 학습시키고, 같은 케이스에 추론해서 정답과 비교합니다. R제곱이 1에 가깝지 않으면 다음 중 하나가 잘못된 것입니다: 필드/좌표 대응, 정규화, checkpoint 로딩, prediction-to-mesh 매핑.

이 게이트를 STL 표면 중심점으로 평가하면 7단계의 문제(법선/면적 불일치)와 섞여서 원인을 잘못 판단하게 됩니다. 먼저 정답 CFD 메시의 점에서 평가해 파이프라인 자체를 검증한 뒤에, 7단계에서 STL 기반 추론을 별도로 검증하세요.

07

추론 스크립트 - 두 가지 함정을 미리 피하기

왜: 학습은 CFD 메시의 점에서 이뤄지지만, 실제 서비스에서는 사용자가 올린 STL의 삼각형에서 값을 물어봐야 합니다. 이 둘은 같은 지오메트리라도 법선 방향과 면 해상도가 다를 수 있습니다.

전체 흐름은 이렇습니다: 1) STL 로드, 2) 면(face)을 배치 단위로 잘라 모델에 질의, 3) 결과를 원래 face 순서로 재조립, 4) STL 메시 위에 값을 얹어 VTP로 저장. 4)는 프레임워크가 대신 해주지 않습니다 - 아래에서 직접 다룹니다. 이 단계에서 다루는 스크립트를 이 가이드에서는 predict_on_stl.py라고 부릅니다. 먼저 2), 3) 단계에서 흔히 발생하는 두 가지 함정부터 보겠습니다.

주의: 파일 이름이 다릅니다

GitHub 저장소를 그대로 clone하면 이 폴더 안의 원본 파일명은 predict_on_stl.py가 아니라 inference_on_stl.py입니다. 이 가이드의 predict_on_stl.py는 그 원본을 복사해서 이번 프로젝트용으로 직접 수정(아래 법선 부호 수정, STL 서브디비전 등)한 파일이라, 처음 받으셨다면 inference_on_stl.py를 기준으로 찾으셔야 합니다.

함정 1 - 법선 부호(sign). STL 파일의 vertex winding 순서가 CFD 메시 쪽과 반대일 수 있습니다. 배포 전에 반드시 검증하세요:

normal = torch.linalg.cross(d2, d1, dim=1)   # (d1, d2) 순서였다면 뒤집기

함정 2 - 면적 해상도. STL이 CFD 메시보다 거칠면(면 개수가 적으면) 각 면의 넓이가 실제보다 크게 계산됩니다. 정답 데이터 없이도 고칠 수 있습니다 - STL을 한 단계 세분화(subdivide)해서 CFD 해상도에 가깝게 만들고, 그 조밀한 점에서 예측한 뒤 원래 면으로 평균을 되돌립니다:

import pyvista as pv
mesh = pv.PolyData(vertices, faces)
mesh.cell_data["orig_id"] = range(mesh.n_cells)
fine = mesh.subdivide(1, subfilter="linear")   # 삼각형 1개 -> 4개
# fine 메시의 중심점/법선/면적으로 예측한 뒤, orig_id로 평균 내서 원래 면 개수로 되돌림
경고: 이 검증을 생략하면

모델은 멀쩡한데 배포된 예측 결과만 계속 나쁘게 나오고, "모델을 더 학습시켜야 하나?"라는 잘못된 결론으로 이어집니다. 실제 사례에서 이 두 버그만으로 R제곱이 -0.31에서 0.99까지 차이가 났습니다 - 모델 재학습 없이 스크립트 수정만으로.

결과를 VTP로 저장하기 - 여기부터는 직접 작성해야 함

모델이 뱉는 건 그냥 숫자 텐서((면 개수, 필드 차원) 크기의 숫자 표, .pt/.npy가 저장하는 것과 같은 종류) 하나뿐입니다. 어떤 메시 위에, 어떤 이름으로, 점 데이터인지 면 데이터인지는 그 표 자체엔 없는 정보라서 프레임워크가 몰라서 정해주지 못합니다 - VTP 파일 구조를 직접 조립해야 합니다.

  1. 추론에 쓴 원본 STL의 정점, 면 연결정보로 pyvista.PolyData를 새로 만듭니다 (추론에 쓴 subdivide된 메시가 아니라 원본 - 뷰어가 사용자가 올린 그 형상 그대로 보게 하려면).
  2. 재조립된 출력 텐서를 mesh.cell_data["필드이름"]에 컬럼 단위로 나눠 씁니다 (scalar=1열, vector=3열) - face당 값 하나이므로 cell_data입니다. 정점당 값(point_data)을 쓰면 안 됩니다 - 필드가 면(face) 중심에서 계산된 것이라서 방식이 다릅니다.
  3. 모델이 직접 내놓지 않은 파생값(예: 압력계수 Cp = 2 * pMean, 무차원 컨벤션에서)은 저장 직전에 여기서 한 번 더 계산해 추가 필드로 넣습니다.
  4. mesh.save("prediction.vtp") - VTK가 실제 파일 쓰기를 담당합니다.
save_prediction.py (Python)
import pyvista as pv
import numpy as np

def save_surface_prediction(stl_coordinates, stl_faces, output_full,
                             field_spec, output_path):
    """
    stl_coordinates : (N_verts, 3)  원본 STL 정점
    stl_faces       : (N_faces*3,)  원본 STL 면 연결정보 (평탄화됨)
    output_full     : (N_faces, D)  재조립된 모델 출력 (face 순서 = 원본 STL과 동일)
    field_spec      : 예) {"pMean": "scalar", "wallShearStressMean": "vector"}
    """
    verts = stl_coordinates.cpu().numpy()
    faces = stl_faces.reshape(-1, 3).cpu().numpy()
    n_faces = faces.shape[0]
    # VTK의 face 배열 형식: [정점개수, i0,i1,i2, 정점개수, i0,i1,i2, ...]
    faces_flat = np.hstack(
        [np.full((n_faces, 1), 3, dtype=np.int64), faces]
    ).reshape(-1)
    mesh = pv.PolyData(verts, faces_flat)

    results = output_full.cpu().numpy()
    offset = 0
    for name, kind in field_spec.items():
        dim = 3 if kind == "vector" else 1
        mesh.cell_data[name] = results[:, offset:offset + dim]   # face당 값 하나
        offset += dim

    # 모델이 직접 내놓지 않은 파생 필드는 여기서 계산
    if "pMean" in mesh.cell_data:
        mesh.cell_data["static(p)_coeffMean"] = 2.0 * mesh.cell_data["pMean"]

    mesh.save(output_path)   # 기본이 바이너리 저장 -- 뷰어 호환성 이유는 아래 참고
경고: 실제로 겪은 저장/호환성 함정
  • ASCII로 저장하면 일부 뷰어(Kit-CAE 등)에서 cell-data 색칠이 안 먹힘 - mesh.save(path, binary=True)(기본값)를 명시적으로 유지할 것
  • 빈 위상 요소(Verts/Lines/Strips 블록이 0개인 채로 헤더에 남는 경우) 때문에 import가 조용히 실패하는 뷰어가 있음 - 저장 후 VTK 텍스트 헤더를 열어 빈 블록을 지우는 후처리 한 단계가 필요할 수 있음
  • 체적(volume) 격자 출력은 메시가 아니라 규칙적인 격자이므로 pyvista.ImageData + .vti 확장자 + point_data를 씁니다 - 표면(surface) 출력과 저장 방식 자체가 다릅니다

평가 방법론

  • 예측 메시와 정답 메시의 해상도(면 개수)가 다르면, index 대응이 아니라 좌표 기반(KDTree) 최근접 매칭으로 비교
  • 같은 모델을 (a) 정답 메시 지점, (b) 실제 배포용 STL 지점 두 가지로 모두 평가 - 격차가 크면 7단계로 돌아가 추론 스크립트를 의심
  • 지표는 MAE/RMSE/R제곱/relative L2를 최소 5~10개 테스트 케이스 평균으로 - 케이스 1~2개로 결론 내지 않기
  • 원인이 애매하면 ablation: 위치/법선/면적처럼 입력을 하나씩 정답값으로 바꿔가며 어떤 것이 점수를 바꾸는지 격리

애플리케이션(Kit-CAE) 연동

왜: 학습/추론 서버와 3D 뷰어가 다른 머신이면 SSH/SCP로 잇는 것이 가장 간단한 시작점입니다.

  • SSH 키 기반 인증 설정 (비밀번호 없이)
  • 확장이 STL을 SCP로 서버에 업로드, 원격 추론 스크립트 실행, 결과 VTP를 SCP로 회수, 뷰어에 import
  • 여러 결과를 나란히 비교하는 화면이라면 색상 범위를 고정할 것 - 자동 스케일은 실제로는 비슷한 두 결과를 다르게, 다른 두 결과를 비슷하게 보이는 착시를 만듭니다
